# signal-insight 团队工程规范

> 本文件给人看，也给编程智能体看。往仓库里加任何文件之前，先读完本文件。
> 每条规则都写了“理由”：只有规则、没有理由的不算写完。【D0x】是这条规则加入的日期。

## 0 项目一句话

用沈阳 2018 年国庆的手机信令样本，回答“国庆傍晚来西塔的人几点来、待多久、从哪来、还去了哪”，
并把分析做成每天能运行、坏数据进不来、结果可追溯、能对外展示的系统。

## 1 数据与合规【D01】

1.1 `data/` 整个不进 Git。库里的 `ods_`、`dwd_`、`dws_` 表能识别到个人。
1.2 `ods_` 表只读，不在上面改数据。要修正就写成新表（`dwd_` 及以后），原始层留作“出了事能回去对账”的依据。
1.3 notebook 的运行结果不进 Git。仓库装了 nbstripout，提交时自动清空；运行结果里可能有 IMSI、手机号、轨迹。
1.4 **不把明细数据行发给大模型。** 可以给表结构、字段名、聚合结果。让智能体跑代码时，输出里不打印完整 IMSI、手机号。
1.5 对外（报告、PPT、简历）只出现聚合结果。
1.6 仓库在 Gitee 上必须是**私有**的。

**理由**：数据一旦进过仓库，删掉也还留在历史里；推到 Gitee 就等于发出去了。

## 2 按“它会因为什么而改”分文件【D02】

一个文件里的代码，应该只因为一种原因而改。新代码放哪，先问“它将来会因为什么而改”：

| 会因为什么而改 | 放哪 |
|---|---|
| 文件放的位置变了；口径常量变了 | `src/signal_insight/config.py` |
| 图表规范变了 | `src/signal_insight/viz/`（D02 时是 `viz.py`） |
| 稽核记录、数据画像的格式变了 | `src/signal_insight/quality.py` |
| 空间算法变了（距离、点落面） | `src/signal_insight/geo.py` |
| 换了数据库 | `src/signal_insight/db.py` |
| 某张表的算法或口径变了 | 这张表对应的模块（见第 5 条）：`dwd.py`、`dims.py`、`dws.py` |
| 运行方式变了 | `src/signal_insight/pipeline.py` |
| 业务参数变了（500 米改 1 公里） | `config/settings.yaml`（不改代码） |
| 只用一次的探索 | 留在 notebook 里，不收 |

**理由**：改一种东西只动一个地方，别人知道去哪找。不同原因的代码混在一起，改 A 的时候容易碰坏 B。

## 3 依赖方向【D02，D05 补全】

```
notebooks/   tests/                       ← 用的人
        ↓
pipeline.py                               ← 编排：唯一同时碰“数据库”和“计算”的地方
        ↓
dwd   dims   dws                          ← 每一层的计算
        ↓
geo   quality   viz/   db                 ← 通用能力
        ↓
config                                    ← 最底层，不 import 项目里任何东西
```

3.1 上层可以 import 下层，下层永远不 import 上层。比如 `dwd` 不能 import `pipeline`（所以 `@step` 套在 `pipeline` 里的小函数上）。
3.2 `src/` 里任何文件都不 import `notebooks/`、`tests/`。
3.3 不允许循环依赖。

**理由**：依赖只往一个方向走，改底层时知道会影响谁，改上层时底层不受影响。

## 4 计算与读写分开【D04 建议，D05 起强制】

4.1 计算模块（`dwd`、`dims`、`geo`、`dws`）只接收 DataFrame 或数字，只返回 DataFrame 或数字。**不连数据库，不读写文件。**
4.2 只有 `db.py`、`pipeline.py` 碰数据库。例外登记：`quality.dq_record` 写稽核表，连接由调用方传入，它自己不开连接。
4.3 函数需要的东西都通过参数传进来，不依赖任何全局变量。
4.4 契约测试会自动检查计算模块里有没有 `import sqlite3`、`read_sql`、`to_sql`。

**理由**：

- 计算不碰库，测试时塞一个十行的 DataFrame 就能测；
- notebook、流水线、以后的报告和平台都能复用同一个函数；
- 换数据库只改 `db.py`。

## 5 代码按数仓分层组织【D03 分层，D04 文件长成文件夹，D05 与表名对应】

5.1 表名前缀就是分层：

| 前缀 | 层 | 说明 |
|---|---|---|
| `ods_` | 原始层 | 数据平台同步来的原样数据，只读，不改一个值 |
| `dwd_` | 明细层 | 清洗后的明细 |
| `dim_` | 维表 | 描述“是什么”的表：基站、热点 |
| `dws_` | 汇总层 | 按人、按天汇总（D06 起） |
| `ads_` | 应用层 | 直接给图表、报告用的结果 |

5.2 生成哪张表的代码，就在哪个模块里：`dwd_signal` 在 `dwd.py`，`dim_cell`、`dim_hotspot` 在 `dims.py`，`dws_stay` 等在 `dws.py`。
5.3 **一个文件出现第二种改动原因，或超过约 300 行，就把模块变成同名文件夹**，一个改动原因一个文件。文件夹的 `__init__.py` 重新导出原来的名字，调用方一行不改（D04：`viz.py` → `viz/theme.py` + `viz/maps.py`）。

**理由**：看到表名就知道这张表处理到了哪一步；看表名还能知道生成它的代码在哪个文件里。

## 6 命名【D02】

6.1 变量、函数、模块，以及库表、CSV、函数返回的表的**列名**，都用英文，小写加下划线。列名的习惯：计数 `n_`、份额 `_share`、比率 `_rate`、单位写在后缀（`_m`、`_min`、`_sec`）、日期分区叫 `dt`。中文放在注释、文档、图上的文字、表里的值；给人看的表头用显示名（D08 起如 `dims.METRIC_LABELS`），notebook 里只为展示拼的小表可以用中文表头。（理由：SQL 里不用再给列名加引号，`"耗时(秒)"` 这种写法很容易错；换到 Hive、BI 工具时也不会因为中文列名出编码问题。）
6.2 模块名是名词，说清它管什么。**不准建 `utils.py`、`common.py`、`helper.py`、`misc.py`**，这类名字什么都能放，最后变成杂物抽屉。
6.3 包名 `signal_insight`（import 用，只能下划线），发行名 `signal-insight`（pip 用）。
6.4 notebook 用两位编号：`D01_项目启动与数据接入.ipynb`。不补零会排成 D1、D10、D11 … D2。
6.5 测试文件名 `test_` 开头，目录结构对照 `src/`。

## 7 import 的时候不做事【D02】

import 一个模块时，不连数据库、不改 `rcParams`、不读文件、不打印、不建文件夹。要做事，提供函数让调用方显式调用，比如 `viz.apply_theme()`、`db.connect()`。

**理由**：否则 import 的顺序会改变程序行为；测试一 import 就连上真库。

## 8 业务参数只在 `config/settings.yaml`【D06】

8.1 代码里不出现业务阈值数字，比如 500 米、30 分钟、17 点、1.5 公里、5 人。默认参数里也不行。全部从 `config.load_settings()` 读，由流水线传给计算函数。
8.2 路径常量在 `config.py`，因为路径由代码位置决定，不由业务决定。
8.3 `settings.yaml` 一律 UTF-8 保存。
8.4 契约测试会扫描汇总层代码里有没有写死的业务数字。

**理由**：参数由业务决定，业务方看得懂 yaml、看不懂 Python；改参数不改代码；每个数字都能追溯到当时用的是哪一版参数。

## 11 测试【D05】

11.1 `tests/contract/` 是讲师给的契约测试，**不许改**。不通过就改自己的代码。
11.2 `tests/unit/` 测单个函数，用手造的小 DataFrame 或读 `ods_` 表；目录结构对照 `src/`（测 `dwd.py` 的叫 `test_dwd.py`）。
11.3 notebook 里的对账格，稳定以后搬进 `tests/unit/`。
11.4 修 bug 的顺序：先写一条会失败的测试，再改代码让它通过。
11.5 提交之前 `python -m pytest` 必须全绿。
11.6 测试只读 `signal_insight`，不在里面建表、写表；要写库就在临时库 `test_course_xxx` 里写（契约测试的 `sandbox`），用完连库删掉、连接关掉。`signal_mysql` 连接的 `with` 只提交、不关连接，关连接要自己写。

**理由**：对账只靠打开 notebook，换个人、换台机器就没人跑了；写成测试，一条命令就知道有没有改坏。测试只写临时库，跑多少遍都不会动 `signal_insight` 里前几天的结果。

## 12 图表【D02】

12.1 出图一律调用 `viz.finish()`，不在 notebook 里手写标题区。
12.2 标题是结论、带数字，数字由代码算；副标题写口径；有来源行。全文见 `docs/图表规范.md`。
12.3 只用开源字体（思源黑体、思源宋体、TeX Gyre Termes），代码里不出现商业字体的名字。
12.4 同一个区域、同一类客群在所有图里同色，颜色取自 `viz` 的固定映射。
12.5 地图用 `viz.maps`：长宽比校正、区县底图、指北针、比例尺。

## 14 Git【D01】

14.1 一次封装一个提交；对账和测试通过后再提交。
14.2 提交说明格式 `类型: 一句话说明`（英文冒号加空格）。类型只用以下几种：

| 类型 | 含义 |
|---|---|
| `feat` | 新功能、新模块 |
| `refactor` | 搬代码、改结构，**结果不变** |
| `fix` | 修错 |
| `test` | 测试 |
| `docs` | 文档 |
| `chore` | 配置、依赖、杂项 |
| `perf` | 性能 |
| `analysis` | notebook 分析进展 |

14.3 不习惯性地 `git add .`：先 `git status`，再点名要提交的文件。
14.4 里程碑打标签：`v0.1`（D05）、`v0.2`（D10）、`v1.0`（D15）。

## 15 给编程智能体的约定【D02】

15.1 新建文件前，先说明放在哪个目录、依据本文件第几条规则；没有合适位置时停下来问，不要自己发明新目录。
15.2 不新建 `utils.py` 一类的文件（第 6.2 条）。
15.3 不读取 `data/` 下的明细数据内容；需要了解数据时，看表结构和 `docs/数据字典.md`。
15.4 不在函数里使用 notebook 的全局变量；需要什么就加参数（第 4 条）。
15.5 不修改 `tests/contract/` 下的任何文件；改完代码后运行 `python -m pytest`，把结果告诉使用者。
15.6 不在代码里写业务阈值数字（第 8 条）；需要新参数时，加到 `config/settings.yaml` 并说明。
